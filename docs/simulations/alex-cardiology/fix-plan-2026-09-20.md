# Online interview fixes after the 25-question baseline

The agreed allowance is **5,000 accepted online LLM requests and 5,000,000 input +
output tokens per organization per UTC day**, shared by its users and devices.
Local model execution has no daily request/token quota. Provider throttling and
speech audio-duration allowances are separate from this LLM allowance.

## Implemented quota correction

- New settings: `PMS_LLM_DAILY_REQUESTS=5000` and
  `PMS_LLM_DAILY_TOTAL_TOKENS=5000000`. Remove the obsolete
  `PMS_LLM_DAILY_OUTPUT_TOKENS` override when upgrading.
- Migration `0017_llm_total_quota` preserves historical output reservations and
  adds combined reservations and settled usage. Online admission locks the
  organization, preventing concurrent callers from spending the same remaining
  capacity. Both limits use the admission day and reset at 00:00 UTC.
- A generated patient answer counts as one accepted request, with input/output
  tokens from both routing and voice calls. Successful complete usage settles
  the reservation. Missing/invalid/partial usage or unsuccessful outcomes keep
  a conservative reservation. Reasoning and cached-token details are subsets,
  so they are not added twice. This is usage control, not a billing report.
- Cached replays do not consume another request or reservation. Rejected
  admissions make no provider call and consume no daily allowance. Local turns
  remain outside online accounting.
- Desktop errors now distinguish the organization's token and request allowance
  and show the UTC reset time. Simulation database snapshots capture combined
  charges/reservations as well as historical output reservations.

## Implemented speech retry policy and visibility

Cloud transcription now allows ten rounds of five retries, with a three-second
pause between rounds. Within each round the existing 1–5 second waits remain.
There is one initial submission and at most 50 retries of the same captured WAV.
A centered bordered status panel shows an animated clock, countdown, elapsed wait,
round/retry progress and cancellation. Success stops retries immediately; quotas,
authorization failures and unknown outcomes still stop instead of being replayed.
Response-model retries remain capped at five.

This bounded policy improves persistence and visibility. Provider-aware
`Retry-After`, shared cooldown and the remaining work below are still open.
The live simulator now budgets all allowed rounds and records structured retry
progress. Original baseline results remain unchanged.

## Remaining work, in priority order

1. **Speech throttling and retry delay.** The baseline recorded 66 upstream HTTP
   429 responses during transcription and 60 automatic retries. Preserve safe
   `Retry-After` metadata and distinguish `speech_busy` from response-model busy
   errors. Coordinate cooldown across callers of the same speech deployment;
   use bounded backoff with jitter and an explicit overall wait deadline. Retry
   only confirmed admission/rate rejections, never an unknown submission. Inspect
   the deployment's actual rate allowance before deciding whether it needs more
   capacity. Test repeated 429s, eventual recovery, cancellation and unknown
   outcomes with mocks before repeating a live load run.

2. **Capacity feedback before recording/transcription.** Expose an authorized,
   organization-scoped daily capacity summary containing limits, used/reserved
   tokens, accepted requests and reset time. Check it before cloud capture and
   refresh after a rejection. Keep server admission authoritative because another
   caller can spend capacity after a precheck. The baseline wasted 13 successful
   transcriptions on turns that could not receive an LLM answer.

3. **Intermittent readiness rejection.** Tag speech and response readiness probes
   separately with safe status, timing and failure stage. The baseline's first
   question failed after approximately five seconds; its failing provider was
   not isolated. Read-only readiness checks can use bounded retry and a short
   freshness cache. Preserve authentication/configuration failures as actionable
   errors, and never treat a successful model-list probe as proof of inference.

4. **Answer latency.** Record routing, voice, validation and first-audio timings.
   Four of five successful baseline turns made two LLM calls; the successful
   response roundtrips ranged from 0.953 to 9.860 seconds. For cases with suitable
   authored answers, evaluate the existing authored-answer mode to avoid the
   second call. Compare correctness against the same case before adopting it.
   Keep generated answers bounded and validated before playback; reducing these
   protections simply to make audio start sooner would change correctness.

5. **Audio completion and visible failure states.** Trace each turn through
   answer accepted, synthesis started, playback started and playback completed.
   Give errors a visible terminal state and clear stale playback work when a
   conversation changes. All five successful baseline answers progressed through
   TTS; later silence mostly followed failed speech or quota-rejected answers.
   The baseline does not establish a separate speaker failure, so investigate
   any successful-answer-without-audio case using these timings.

## Repeated acceptance test

Keep the existing baseline folder unchanged. Run `run.bat --gap-seconds 1` from
this directory after applying each fix; it saves a fresh timestamped result
folder. Fast question pacing should still respect provider cooldown. Use the same
25 questions and record final failures, recovered retries, request counts, total
usage, latency and playback completion. Compare the first/last turns for memory
or playback degradation. The target is all 25 valid questions completing with
expected transcripts, grounded answers and audio, while a separate overload run
verifies controlled errors and recovery. Automated topic/content checks support
manual answer review; they do not establish complete clinical correctness.

The quota implementation and mocked integration tests do not establish that
upstream speech throttling or live audio failures are fixed. Those need a new
live run after the relevant changes.

## Local verification after resuming

Read-only inspection confirmed the already-running demo uses migration
`0017_llm_total_quota`, with defaults of 5,000 requests and 5,000,000 combined
tokens, and `/health/ready` returned HTTP 200. The snapshot contained 52 accepted
requests and 111,355 tokens charged or reserved today: 62,203 reported tokens plus
49,152 retained across three failed requests with uncertain usage. These are a
point-in-time snapshot, not a fixed allowance remaining.

The normal launcher had already upgraded the schema. The stopped-demo upgrade
helper refused to run against the active stack before changing anything; the
subsequent check was read-only. No running service was restarted and no cloud
inference was submitted for this verification. Recent app, capture, configuration,
cloud-audio and VAD changes were preserved. Evidence is under
`.test_artifacts/org-total-token-quota/` (local, untracked).
